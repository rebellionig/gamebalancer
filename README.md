# Game Balancer — многоагентная система балансировки игры

Агенты итеративно подбирают параметры юнитов (`balance.json`) тактической игры 5×5 так, чтобы винрейты сторон и юнитов были в диапазоне 45–55%.

## Тема и обоснование многоагентного подхода

**Задача.** Дизайнер игры вручную правит параметры юнитов (здоровье, урон, дальность) и долго проверяет, не появилась ли доминирующая стратегия. Система автоматизирует цикл «предложить правку → проверить → смоделировать → проанализировать → отчитаться», пока баланс не сойдётся.

## Для кого это программа?
- Геймдизайнеров и разработчиков игр — чтобы автоматизировать длительную ручную работу по настройке игрового баланса (характеристик персонажей, здоровья, урона, дальности атаки и т. д.). В место ручного тестирования система самостоятельно проводит симуляции матчей, анализирует статистику побед (винрейты) и предлагает оптимальные изменения.
- Студентов и исследовательских команд (в описании упоминается «Ассайнмент 2») — как учебный или исследовательский проект для изучения многоагентных систем (Multi-Agent Systems), работы с LLM (большими языковыми моделями), симуляций и автоматического проведения z-тестов.

## Основные возможности и целевая аудитория

- Автоматическая балансировка: Агенты подбирают параметры юнитов так, чтобы процент побед сторон и персонажей находился в целевом диапазоне (45–55%)
- Разделение ролей агентов: В системе работают специализированные агенты — Дизайнер (генерирует идеи), Критик (проверяет на эксплойты), Симулятор (запускает матчи) и Аналитик (проверяет статистику).

## Чем она полезна?

- Программа Game Balancer полезна тем, что решает главную проблему игровой разработки — высокую трудоёмкость, субъективность и медлительность ручной настройки баланса.

## Как именно она работает?

Система запускает непрерывный автоматический цикл оптимизации:
- Генерация гипотезы (Дизайнер / LLM): Предлагает изменить параметры юнитов (например, снизить урон лучнику или увеличить здоровье воину)
- Первичный фильтр (Критик): Проверяет правку на адекватность и отсутствие очевидных синергий/эксплойтов до симуляции
- Массовая симуляция (Симулятор): Запускает сотни/тысячи автоматических матчей между ботами с новыми параметрами
- Математическая оценка (Аналитик): С помощью статистических тестов (z-тест) отделяет случайную погрешность от реального дисбаланса
- Принятие решения (Оркестратор): Проверяет, достигнут ли целевой винрейт (45–55%), и либо завершает работу, либо отправляет баланс на новую итерацию
- Отчётность (Репортёр): Формирует понятный Markdown-документ с историей всех изменений и выводами.

## В чём её главная польза и преимущество?

- Экономия времени геймдизайнеров: Вместо того чтобы вручную менять таблицы, запускать тесты и сыграть десятки матчей, разработчик получает готовый сбалансированный конфиг и отчёт за считанные минуты.
- Объективность и точность: Решения принимаются не на основе интуиции или мнения нейросети, а на основе реальной математической статистики и детерминированного кода игры (процент побед стремится к 50%).
- Защита от «галлюцинаций» нейросети: Благодаря распределению ролей (многоагентный подход) LLM не оценивает сама себя — её идеи жёстко валидируются кодом симулятора и агентом-критиком
- Поиск сложных эксплойтов и крайних случаев: ИИ может прогнать тысячи сценариев и найти имбалансные связки юнитов, которые человек мог бы не замечать неделями
- Воспроизводимость и логирование: Все запуски детерминированы (зафиксирован seed) и логируются, что позволяет точно понять, почему именно было принято то или иное решение.

**Почему команда агентов, а не один:**
1. **Разные типы работы.** Генерация идей (LLM), массовые симуляции (код), статистика (z-тест), поиск эксплойтов (пробные матчи), текстовый отчёт. Для каждой нужны свои инструменты и свой контекст.
2. **Независимая проверка.** Дизайнер не оценивает собственную правку: её проверяет Критик, а результат оценивает Аналитик. Один агент так сам себя не проверит.
3. **Измеримость.** Качество проверяется кодом игры (винрейт стремится к 50%), а не мнением LLM: LLM только предлагает, проверяет детерминированный код.
4. **Контроль нагрузки и сбоев.** Каждый вызов агента и инструмента логируется, что позволяет подтвердить распределение нагрузки (ни один агент не выполняет более 40% вызовов) и перезапускать только упавший шаг.

## Игра

Поле 5×5, две стороны по 3 юнита, три типа: `warrior` (ближний бой, много HP), `archer` (дальний бой, мало HP), `mage` (урон по области). Параметры каждого: `hp`, `atk`, `move`, `range`. Порядок хода выбирается случайно в каждом матче (иначе второй ходящий выигрывает ~60%). Боты трёх стратегий: random, greedy, focus. Движок детерминирован по seed.

## Архитектура (прототип, Ассайнмент 2)

```
Оркестратор → Дизайнер → Критик → Симулятор → Аналитик → (Оркестратор проверяет сходимость) → Репортёр
                 ▲         │ (отказ: назад к Дизайнеру, до 2 раз)
                 └─────────┘          AnalysisReport возвращается Дизайнеру
```

| Агент | Роль | Вход → Выход | Инструменты | Статус |
|---|---|---|---|---|
| Оркестратор | только планирует, лимиты итераций/времени | SimResult → решение «дальше / стоп» | SQLite (состояние) | готов |
| Дизайнер | предлагает правки баланса | AnalysisReport → ChangeProposal | LLM | готов (LLM + запасное правило) |
| Симулятор | применяет правки, гоняет батч матчей | ChangeProposal → SimResult | движок игры | готов |
| Аналитик | отличает реальный дисбаланс от шума (z-тест) | SimResult → AnalysisReport | код (статистика) | готов |
| Критик | проверяет правку до симуляции: шаг, направление, жёсткие контры | ChangeProposal → CritiqueReport | пробные матчи (код) | готов |
| Репортёр | итоговый отчёт: изменения баланса, ход итераций, выводы | история → reports/report_<run>.md | запись файла, LLM (только текст вывода) | готов |

Сообщения — pydantic-модели (`messages.py`). Состояние задачи — SQLite (`state/state.db`). Каждый вызов агентов и инструментов пишется в `logs/run.jsonl`.

Схема: `docs/architecture.png`, полная спецификация агентов: `docs/agents.md`.
Пример прогона на сломанном балансе (лог всех вызовов, отчёт, распределение нагрузки): `docs/sample_run/`.

## Запуск

```bash
pip install pydantic pytest
cp .env.example .env        # LLM_API_KEY, LLM_MODEL (и LLM_BASE_URL при необходимости); без них Дизайнер работает по запасному правилу
python main.py --iters 8 --matches 500 --seed 42
python tools_load_report.py # распределение нагрузки по логам
pytest -q                   # тесты

# сценарий с заведомо сломанным балансом (лучник слишком силён)
python main.py --balance scenarios/archer_op.json --matches 1000
```

## Надёжность
- Лимиты: `--iters` (шаги) и `max_seconds` (время) в оркестраторе.
- Определение цикла: если баланс вернулся в уже пройденное состояние, `stop_reason=cycle`.
- Невалидная правка баланса отклоняется (`game/balance.py`), итерация пропускается.
- Ошибки движка: до 2 повторов, затем понятное исключение.
- Движок детерминирован по seed — прогоны воспроизводимы.
