# Спецификация агентов

Схема взаимодействия: **оркестратор + цикл «предложить → проверить → смоделировать → проанализировать»**, общее состояние в SQLite, все вызовы в `logs/run.jsonl`.
Схема: `architecture.png` (исходник `architecture.mmd`).

| # | Агент | Роль (одна) | Вход | Выход | Инструменты (≤5) | Критерий завершения |
|---|---|---|---|---|---|---|
| 1 | Оркестратор | Планирует итерации и распределяет задачи; предметной работы не делает | цель, `AnalysisReport`, `CritiqueReport` | решение «дальше / стоп» и сообщения агентам | SQLite (состояние) | сошлось (винрейты в 45-55%) / лимит итераций / лимит времени |
| 2 | Дизайнер | Предлагает правки `balance.json` | баланс, последний `AnalysisReport` | `ChangeProposal` | LLM | валидный `ChangeProposal` (JSON проходит схему) |
| 3 | Критик | Независимо проверяет правку ДО симуляции | `ChangeProposal`, баланс, `AnalysisReport` | `CritiqueReport` (approved + issues) | пробные матчи «чистых» команд (код) | вердикт выдан |
| 4 | Симулятор | Применяет правку и гоняет батч матчей | одобренный `ChangeProposal`, N, seed | `SimResult` | движок игры | батч выполнен или исчерпаны повторы |
| 5 | Аналитик | Считает статистику и находит «сломанные» значения | `SimResult` | `AnalysisReport` | код (статистика, z-тест) | отчёт сформирован |
| 6 | Репортёр | Собирает итоговый отчёт и patch notes | история итераций | `report.md` | LLM, запись файла | файл записан |

## Форматы сообщений (JSON, схемы в `messages.py`)

- `ChangeProposal`: `iteration`, `changes[1..3]` (`unit`, `param`, `from`, `to`), `rationale`
- `SimResult`: `iteration`, `balance_hash`, `n_matches`, `side_winrate`, `draw_rate`, `unit_winrate`, `avg_turns`
- `AnalysisReport`: `iteration`, `n_matches`, `balanced`, `findings[]` (`metric`, `winrate`, `deviation`, `z`, `verdict`), `worst`, `side_warning`
- `CritiqueReport`: `iteration`, `approved`, `issues[]` (`code`, `message`), `probe` (матрица пробных матчей)
  - коды замечаний: `invalid_change`, `from_mismatch`, `step_too_large`, `wrong_direction`, `exploit_worse`
  - при отказе оркестратор возвращает правку Дизайнеру с замечаниями, максимум 2 раза за итерацию; затем итерация пропускается

## Обоснование распределения нагрузки (≤40% на агента)

Типовой сценарий: ~5 итераций.

| Агент | Вызовов LLM + инструментов за итерацию | Оценка доли |
|---|---|---|
| Дизайнер | 1 LLM (+ до 2 при исправлении JSON и возвратах от Критика) | ~25% |
| Критик | 1 вызов пробных матчей | ~20% |
| Симулятор | 1 вызов движка (батч) | ~15% |
| Аналитик | 1 расчёт | ~20% |
| Репортёр | 1 LLM в конце | ~10% |
| Оркестратор | обращения к SQLite (не считаются как LLM/инструмент предметной работы) | - |

Замер без LLM (запасное правило), 4 итерации, сценарий `archer_op`: Симулятор 36%, Аналитик 36%, Критик 27%. Остальная оценка предварительная: итоговые цифры берутся из `python tools_load_report.py` после полного прогона. Ключевое решение: Симулятор запускает матчи **батчем**, иначе он набрал бы сотни вызовов и превысил 40%.

## Почему именно команда агентов

1. Разные типы работы: генерация идей (LLM), массовые симуляции (код), статистика, поиск эксплойтов.
2. Независимая проверка: Критик не зависит от Дизайнера и не «оценивает собственную работу».
3. Обратная связь в цикле: каждый шаг логируется и ограничен по лимитам.
4. Нагрузку на каждую роль можно измерить по логам.
